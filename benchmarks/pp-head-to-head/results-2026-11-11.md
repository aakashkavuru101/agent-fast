# Head-to-head on real Power Platform work (2026-11-11)

agent-fast vs Claude in Chrome vs Playwright MCP on the BM2 task in `PLAN.md`: three rounds of maker portal home, apps list, open a canvas app in Power Apps Studio, select a button, read its `OnSelect` formula, close Studio without changes. Same model, same machine, same sandbox environment, same browser binary. **One run per tool.**

## Results

| Tool | Wall s | Browser calls | Errors | Retries | Median ms | p95 ms | Model turns | Input tokens | Output tokens | Cost USD | Success |
|---|---|---|---|---|---|---|---|---|---|---|---|
| agent-fast | **260.9** | 58 | 11 | 3 | **85** | 30036 | 36 | 2,327,315 | 9,690 | 1.54 | yes |
| Claude in Chrome | 270.2 | **33** | **4** | 0 | 3364 | **15840** | **33** | **1,076,540** | 9,772 | **0.79** | yes |
| Playwright MCP | 539.9 | 49 | 5 | 0 | 672 | 30018 | 49 | 1,760,498 | 14,243 | 1.05 | yes |

All three runs read the formula correctly in all three rounds, and the app was unchanged after each run: Studio's Save stayed disabled, and `pac canvas list` showed the same Modified date before and after every run.

What the model got back, and where the time went:

| Tool | Tool output (text chars) | Images | Context at the last turn | Most time in (total, calls) |
|---|---|---|---|---|
| agent-fast | 158,000 (snapshots 132,000 in 11 calls) | 6 | 121k tokens | wait_for 76 s (7), screenshot 32 s (6), snapshot 30 s (11) |
| Claude in Chrome | 18,000 | 39 | 63k tokens | browser_batch 130 s (23), find 14 s (2) |
| Playwright MCP | 73,000 (find 39,000 in 10 calls) | 2 | 62k tokens | browser_run_code_unsafe 295 s (19), click 19 s (8) |

Per-call latency is not comparable across tools: a Claude in Chrome `browser_batch` holds a click, a wait and a screenshot, and a Playwright `browser_run_code_unsafe` call holds a whole script, waits included. Wall time, turns, tokens and errors are comparable.

## Verdict

- **agent-fast wins on speed.** It had the shortest wall time and by far the fastest single actions (median 85 ms). It read Studio through text (snapshots, refs inside the iframe) without running arbitrary code. Its lead over Claude in Chrome (9 s) is within one run's noise. Its lead over Playwright MCP (2×) is not.
- **agent-fast loses on errors and cost.** It had the most errors (11), and it used 2.2× the input tokens of Claude in Chrome, at 1.9× the cost. Both causes are fixable in agent-fast; see the fixes below.
- **Claude in Chrome was the most efficient.** It needed the fewest calls, errors, turns and tokens, because it worked by sight. It batched coordinate clicks with screenshots and read the formula off a zoomed screenshot, not from text. That worked here but is fragile: in round 2 the layout shifted and the clicks had to be re-aimed. Two of its four errors were the extension's one-time site-permission prompt.
- **Playwright MCP was the slowest and the least contained.** 19 of its 49 calls were `browser_run_code_unsafe`, arbitrary Playwright code the model wrote against Studio's iframe. Four long built-in waits cost it time: 91 s for Studio to load, a 90 s timeout while the Welcome dialog hid the button, and two 30 s timeouts. agent-fast has no such tool by design (a closed tool catalog).

## Where the time went

| Tool | Wall | Browser busy | of which failed waits of 10 s or more | Model time |
|---|---|---|---|---|
| agent-fast | 261 s | 129 s | 75 s (plus a 30 s first snapshot that succeeded) | 132 s |
| Claude in Chrome | 270 s | 151 s | 0 s | 119 s |
| Playwright MCP | 540 s | 329 s | 151 s | 211 s |

Browser busy is the union of all tool-call intervals; model time is the rest of the wall time. Model time per turn was about the same for agent-fast and Claude in Chrome (3.7 s and 3.6 s). agent-fast's useful browser work came to about 25 s against Claude in Chrome's 151 s: its engine is much faster, and it gave the lead back in timeouts on Studio's iframe. Without those it would have finished in about 155 s.

## Why agent-fast was slower or costlier than it needs to be

| Where | Cost in this run | Cause |
|---|---|---|
| `wait_for` text inside Studio | 30 s timeout | AF-3: text waits do not look inside iframes |
| `wait_for` load `networkidle` in Studio | 30 s timeout | Studio never goes network-idle; with AF-3 the model has no working wait for Studio |
| `click_text` "Skip"/"Leave" and a `batch` click on Studio's dialogs | 3 errors, and a 15 s URL wait after the failed Leave | **AF-9 (new):** only the `click` tool falls back to the on-screen click when an element is "covered" (`src/agent.ts`, `call.name === "click"`); `click_text` and `batch` click steps do not |
| `frame` then `get_text` with a selector (4 tries, `body` included) | 4 errors | AF-4 |
| Formula reading | 6 screenshots, formula bar widened by hand | AF-5: the formula bar exposes only its first line |
| Snapshot size | 132,000 chars in 11 snapshots; context reached 121k tokens vs 62k for the others | **AF-10 (new):** each MCP snapshot result carries a `refs` map that repeats the role and name of every ref already in the tree. That is 48% of the snapshot characters in this run |
| First snapshot after `open` | 29.7 s | Not reproduced: the same open and snapshot from the CLI took 0–1 s. Likely the snapshot ran during the sign-in redirect; watch for it |
| `batch` replay "no menuitem named Apps" | 1 error | The portal renames the Apps item ("Apps, press right arrow…") while its flyout is open. Playwright hit the same; not agent-fast specific |

## Fixes that would move agent-fast's numbers most

1. **AF-3: frame-aware text waits.** Removes the 30 s timeouts in Studio and gives the model a wait that works there. That also avoids the `networkidle` timeout, which the model only tried because the text wait failed. About 60 s of this run's 261 s.
2. **AF-10: drop `refs` from MCP snapshot results** (the engine still uses them internally). That would cut about 63,000 of the 158,000 characters agent-fast returned, roughly half of each snapshot. Every later turn re-reads the context, so this compounds into input tokens and cost, where agent-fast lost most clearly.
3. **AF-9: route `click_text` and `batch` click steps through the same covered-click fallback as `click`.** That removes 3 errors and the 15 s wait that followed one of them.
4. **AF-4 and AF-5: selector reads in Studio's frame and the full formula text.** Together they cost 4 errors and 6 screenshots, the screenshots being the model reading the formula by eye.

## Against the earlier harness run

The harness BM2 row in `../power-platform-live.md` was measured with the harness guard and rules on: 57 calls, 11 errors, median 1453 ms, p95 30240 ms, about 7.7 min. Plain agent-fast here made about the same calls (58) and the same errors (11) in 4.3 min, with a median of 85 ms. The same two 30 s timeouts set the p95 in both.

## Method

- **Runner** `run.mjs`: `claude -p <prompt> --output-format stream-json --verbose --model claude-opus-5-5 --effort xhigh --setting-sources project,local --tools "" --strict-mcp-config --allowedTools mcp__<server> --permission-mode dontAsk --disable-slash-commands`, plus `--mcp-config <tool>.mcp.json` or `--chrome`. Every stream line is timestamped on arrival and saved to `runs/` (git-ignored).
  - `--tools ""` removes every built-in tool (shell, files, web) instead of listing them in `--disallowedTools`. `--setting-sources project,local` keeps user hooks and plugins out, so the sessions ran with no guard and no plugins on any tool. The init line of each run lists only that tool's MCP tools.
  - Claude in Chrome ran in print mode with `--chrome`, so no interactive fallback was needed.
- **Summary** `summarize.mjs`, tested in `test/pp-head-to-head.test.mjs`.
  - Wall time runs from the first to the last stream line. Per-call latency runs from a tool use line to its result line, so calls the client queued behind a parallel call include the queue time.
  - A retry is the same tool called again right after it failed. Model turns are distinct assistant messages. Tokens are the final `result` line's usage: input includes cache reads and cache writes.
  - Success means the formula's first line appears in the final answer.
- **Browser:** Brave for all three. agent-fast and Playwright MCP launch it with `--executable-path` and a dedicated bench profile; Claude in Chrome uses the extension in the tester's own Brave. Google Chrome was not installed.
- **Playwright output:** during the run Playwright MCP wrote its page snapshots into the working directory (moved out, git-ignored); `playwright.mcp.json` now sets `--output-dir` outside the repo. Timing is unaffected.
- **Order:** agent-fast, Playwright MCP, Claude in Chrome, one at a time; each tool's browser was closed before the next run.
- **Versions:** `@aakashkavuru101/agent-fast@0.3.0` (global npm install), `@playwright/mcp@0.0.83` (0.0.84 was under two weeks old), Claude Code 2.1.322, `claude-opus-5-5` at effort xhigh, Brave 1.99.56 (Chromium 157), Node 26.12.1, macOS arm64.

## Caveats

- **One run per tool.** The model takes different paths each time: Playwright's round 2 lost 90 s on a single wait it chose. A second run in reverse order would show the spread.
- **Studio's own load time varies widely,** from about 7 s (warm) to about 60 s (the earlier harness run), and the run order may favour later runs with warmer server-side caches. agent-fast ran first.
- **Claude in Chrome's per-call figures are batches,** and its formula reading is visual. A wrong read would not show up as an error.
- **The success check is a substring match** on the final answer, confirmed here by reading all three answers.
