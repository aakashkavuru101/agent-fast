# Head-to-head results (2026-11-12)

Agent-fast 0.4.0 against four other browser tools for AI agents, on the ten tasks in [README.md](README.md): eight deterministic local pages and two public pages (an MDN reference page and a GitHub repository). Same model (`claude-opus-5-5`, effort xhigh, Claude Code 2.1.322), same machine (macOS arm64, Node 26.12.1), same Brave binary (Chromium 157), one `claude -p` session per task, one run per tool.

## What it showed

- **Every tool completed every task**, and no tool followed the injected instruction on the prompt-injection page.
- **agent-fast was fastest on every task but one**, with the fewest browser calls, the fewest model turns, the fewest tokens, and no errors. Its navigation results carry the new page, so most tasks were one or two calls: `read` alone answered the MDN, GitHub, and table-lookup tasks. Against its own engine exposed directly (agent-browser's MCP server) it used 85% fewer input tokens and half the calls for the same answers.
- **Playwright MCP and Chrome DevTools MCP** were a third slower with no errors, on roughly 50% more browser calls. Playwright's run was the cheapest in API-equivalent dollars because a larger share of its tokens were cache reads.
- **agent-browser's four errors** were on the confirm dialog, which its MCP server could not accept directly. **Claude in Chrome** was the slowest without errors: it works by screenshots in the visible browser, so every task took three calls and the most tokens after agent-browser.

## What the first run taught, and what changed

The first agent-fast run on the same build finished in 133 s with 26 calls, 3 errors, and 427,059 input tokens. Splitting its wall time showed the browser at 7% of it: the gap to Playwright and DevTools was model time per turn, about one second more per turn over 38 turns. Three changes followed, all in 0.4.0:

| Change | Why | Effect in the rerun |
|---|---|---|
| A lean default tool catalog (25 tools, about 2.8k tokens, from 41 tools and 4.1k) with shorter descriptions; `--tools full` restores the rest | The catalog is re-read on every turn, and more choices mean more deliberation | Model time per turn fell from 3.3 s to 2.2 s; input tokens fell 36% |
| No screenshot on a failed read (`get_text`, `snapshot`), only on a failed interaction; the server instructions say not to guess CSS selectors | All three errors were guessed selectors on reads, and each carried an image the model then processed | 0 errors, no images |
| The browser starts at MCP `initialize`, while the model is deciding its first call | A fresh session's first engine call paid about 0.6 s for the launch | Browser time fell from 9.6 s to 3.1 s across the ten tasks; median call 44 ms |

The URL-read fix for blocking dialogs (first run: 110 s on the confirm-dialog task, 30 s per read) is also in 0.4.0. The other four columns were measured once and not rerun.

## Caveats

- One run per tool. A model takes different paths each time; the per-task numbers move by several seconds between runs.
- Claude in Chrome ran in the tester's own visible Brave with the tester's sign-ins; the others ran headless in isolated profiles.
- Public pages change. The MDN and GitHub answers are stable facts, but their page sizes are not.
- Browser Use could not be installed on the benchmark machine and is not in this run; its configuration is in the directory for a later run.
