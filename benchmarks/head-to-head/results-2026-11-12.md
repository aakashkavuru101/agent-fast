# Head-to-head results (2026-11-12)

Agent-fast 0.4.0 against four other browser tools for AI agents, on the ten tasks in [README.md](README.md): eight deterministic local pages and two public pages (an MDN reference page and a GitHub repository). Same model (`claude-opus-5-5`, effort xhigh, Claude Code 2.1.322), same machine (macOS arm64, Node 26.12.1), same Brave binary (Chromium 157), one `claude -p` session per task, one run per tool.

## What it showed

- **Every tool completed every task**, and no tool followed the injected instruction on the prompt-injection page.
- **agent-fast needed the fewest browser calls and the fewest tokens.** Its navigation results carry the new page, so most tasks were one or two calls: `read` alone answered the MDN task and the table lookup. Against its own engine exposed directly (agent-browser's MCP server), it used 77% fewer input tokens and 38% fewer calls for the same answers; the engine's raw results repeat a refs map and the model re-reads it every turn.
- **Playwright MCP and Chrome DevTools MCP were fastest on wall time**, 20 to 25% ahead of agent-fast, with no errors. Their per-call latency is also lower, because agent-fast reads the URL before and after each action that may navigate and appends the new page tree when it did. That costs about 0.5 s per action and saves a model turn; on these short tasks the turn saved was worth less than the time spent.
- **agent-fast's three errors were guessed CSS selectors** (`[role=status]`, `.Layout-sidebar`, `aside`) that did not exist on the page. Each returned "not found" with a screenshot, and the model recovered by reading the tree. The other tools' find and snapshot APIs did not invite guessing. agent-browser's four errors were on the confirm dialog, which its MCP server could not accept directly.
- **Claude in Chrome was the slowest** without errors: it works by screenshots in the visible browser, so every task took three calls and the most tokens after agent-browser.

## A fix this run found

In the first agent-fast run the confirm-dialog task took 110 s: the engine answered the click instantly and reported the open dialog, but agent-fast's URL read after the click, and again before `dialog accept`, blocked for the engine's full 30 s timeout each. 0.4.0 skips those reads while a dialog is open, so the task takes 26 s. The agent-fast column above is a rerun on the fixed build; the other columns were not rerun. The full test suite now checks that a click that opens a dialog and the answer to it both return in under 5 s.

## Caveats

- One run per tool. A model takes different paths each time; the per-task numbers move by several seconds between runs.
- Claude in Chrome ran in the tester's own visible Brave with the tester's sign-ins; the others ran headless in isolated profiles.
- Public pages change. The MDN and GitHub answers are stable facts, but their page sizes are not.
- Browser Use could not be installed on the benchmark machine and is not in this run; its configuration is in the directory for a later run.
